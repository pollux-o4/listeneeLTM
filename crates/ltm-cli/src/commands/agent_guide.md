# Listen to Me (LTM)

이 프로젝트는 LTM으로 과업지시서·프롬프트를 작성한다. 사용자가 "LTM으로 …", 과업지시서·프롬프트 작성·다듬기·점검을 요청하면 따른다.

명령 탐색: `ltm`이 PATH에 없고 프로젝트에 `node_modules/.bin/ltm`(Windows: `ltm.cmd`)이 있으면 아래의 모든 `ltm` 명령을 `pnpm exec ltm` 또는 해당 로컬 실행 파일로 실행한다.

## 흐름

0. 첫 명령은 `ltm pref show && ltm list` 한 번이다. 취향 노트(이 사용자의 판단 기준)를 따르고, 확인 전 항목은 약한 근거로 다룬다.
1. 이어 쓸 지시서가 있으면 고른다. 없으면 맥락을 읽기 전에 `ltm new <id> "<제목>"`부터 실행한다(id: 소문자·숫자·하이픈). 사용자가 GUI에서 지시서가 나타나기를 기다리고 있다. 비슷한 지시서가 있으면 `--from <원본 id>`로 복제한다(항목은 확인 전으로 바뀐다).
   - 과업이 말해지지 않았으면("LTM으로 과업지시서 써보자") 되묻지 않는다. 대화·진행 중 작업(커밋 안 된 변경, 최근 커밋, 미결 결정)에서 가장 그럴듯한 과업으로 시작하고 "○○로 시작했어요, 다르면 말해 주세요"라고 한 줄로 알린다. 단서가 전혀 없을 때만 한 문장으로 묻는다.
2. 프로젝트 파일·결정 기록·대화에서 목적·범위·제약·완료 기준을 직접 찾아 채운다. 사용자 지식으로 채울 일을 되묻지 않는다.
3. 판단이 필요한 곳은 갈림길로 만든다. 직접 정할지 열어 둘지는 취향 노트의 `결정` 기준을 따르고, 기준이 없으면:
   - 업계 관행으로 답이 자명하고 되돌리기 쉬운 선택: `"decide": true`로 추천대로 정해 둔다(사용자가 GUI에서 바꿀 수 있다).
   - 취향·비용·되돌리기 어려운 선택·충돌: 열어 두고 사용자에게 한 줄로 알린다.
   - (2·3 공통) 어디에 무엇을 쓰는가. 어기면 `ltm set`이 저장하지 않고 사유와 고치는 방법을 돌려주니, 그대로 고쳐 다시 보낸다.
     - 항목 `text`·질문·선택지 `label`·`text`: 한 뜻의 짧은 한 문장("~를 ~하게 한다", 40자 이내). 괄호·화살표·백틱·풀어 쓰지 않은 영문 약어(AI 제외)를 쓰지 않는다. 다른 뜻이면 항목을 나눈다.
     - `detail`(항목): 모든 항목에 설명과 기술을 채운다. 설명은 일상어 `- 줄`(풀이·조건), 기술은 전체를 `[ ]`로 싼 `- [줄]`(무엇을 어떻게 구현하는지, 명령어·약어 허용). 예: `"- 개발하며 계속 갱신해요\n- [mise run tasks에 refresh를 붙여 빌드 후 이전 서버를 닫고 다시 띄운다]"`. 줄당 100자 이내, 최대 6줄, 정말 없는 칸만 비운다(화면에 '없음'으로 보인다). `why`·`note`: 일상어 한두 문장. 사람이 궁금할 때만 펼쳐 보고, 최종 지시서에는 제목 아래에 함께 들어간다. 수신자에게 꼭 필요한 조건은 여기에 넣는다.
     - 앞 갈림길의 선택에 따라서만 의미 있는 갈림길에는 `"when":{"decision":"<앞 갈림길 id>","options":["<선택지 id>"]}`를 붙인다(앞 갈림길을 먼저 만든다). 조건이 맞지 않으면 화면에 잠금으로 보이고 막힘이 아니며, LTM이 문장 넣고 빼기를 맞춘다. 서로 배타인 선택은 갈림길 하나의 선택지로 만든다.
     - 질문은 "이걸 정하면 무엇이 달라지는가"로 묻고, `note`에는 결과·비용·되돌리기 쉬운지를 쓴다. 사람이 판단할 수 없는 기술 선택은 `"decide": true`로 정하고 한 줄로 알린다.
4. `ltm check <id>`의 `ready`가 true가 될 때까지 막힘(`issues`의 `blocking`)을 해소한다.
   - 출력에 `selfReview`가 있으면 사용자에게 끝났다고 말하기 전에 그 지시를 따른다: `standard`(제품 한 줄)에 비춰 지시서를 적대적으로 리뷰하고 한 번 고친 뒤 `markReviewed`로 표시한다. 사용자에게 묻지 않고, 고친 점을 한 줄로 알린다.
4-1. 사용자가 "LTM 요청 봐 줘"처럼 말하면 `ltm check <id>`의 `requests` 지시대로 열린 요청(`brief.requests`)을 처리한다. 먼저 `takeRequests`로 맡았음을 표시하고(사용자 화면에 '처리 중'), 묻는 말엔 답하고, 고칠 것은 고친 뒤 `resolveRequest`로 한 줄 답을 남긴다.
5. 지시서 작업을 마치면 아래 취향 노트 규칙대로 분석하고 `ltm set <id> '{"op":"markAnalyzed"}'`로 표시한다. 배운 것이 없어도 표시한다(목록의 학습 상태: `unanalyzed`·`stale`이면 다시 분석).
6. 사용자에게 `ltm ui`(http://127.0.0.1:4318)에서 보고 고칠 수 있다고 알린다. 최종본은 `ltm export <id>`(막힘이 남아 있으면 stderr에 초안임을 알린다).

## 편집: `ltm set <id> '<JSON>'`

형식의 원본은 `ltm schema`(JSON Schema)다. 아래 표는 자주 쓰는 예시다.

섹션: `purpose`(목적) · `scopeIn`(포함 범위) · `scopeOut`(제외 범위) · `constraints`(제약) · `acceptance`(완료 기준)

| op | 예 |
| - | - |
| addItem | `{"op":"addItem","section":"purpose","text":"...","detail":"..."}` (`detail` 선택) |
| editItem / removeItem | `{"op":"editItem","id":"i3-0","text":"...","detail":"..."}`(`detail` 생략 시 유지, `""`이면 삭제) · `{"op":"removeItem","id":"i3-0"}` |
| ask | `{"op":"ask","decision":{"id":"image-host","section":"constraints","question":"이미지를 어디에 둘까?","why":"비용·속도를 정한다","recommended":"static","decide":true,"options":[{"id":"static","label":"정적 호스팅","note":"무료","text":"이미지는 정적 호스팅"},{"id":"cdn","label":"CDN","note":"월 비용","text":"이미지는 CDN"}]}}` (선택지에 `"section":"scopeOut"`처럼 문장이 들어갈 섹션을 따로 지정할 수 있다) |
| choose | `{"op":"choose","decision":"image-host","option":"cdn"}` |
| setTitle | `{"op":"setTitle","value":"..."}` |
| markAnalyzed / markReviewed | `{"op":"markAnalyzed"}` · `{"op":"markReviewed"}` |

- 문장은 한 줄로 쓴다(줄바꿈은 한 칸으로 접힌다). 여러 내용은 항목을 나눠 적는다.
- 갈림길 선택지는 2개 이상, id는 서로 다르게(소문자·숫자·하이픈), `label`과 `text`는 비우지 않는다.
- 사람이 GUI에서 고친 내용이 우선이다. 쓰기 전에 `ltm check`로 최신 상태를 읽는다.
- AI가 쓴 항목은 사람이 확인할 때까지 "확인 전"으로 표시된다. 사람의 확인을 대신하지 않는다.
- 실수는 `ltm undo <id>`.

## 취향 노트: `ltm pref set '<JSON>'`

사용자의 요청·지적·선택에서 반복되는 판단 기준을 기록한다. 사용자에게 채우라고 하지 않는다.

- 기록: `{"op":"note","topic":"결정","statement":"자명한 선택은 묻지 말고 정한 뒤 알린다","evidence":"기본값을 묻자 알아서 정하라고 함","brief":"<지시서 id>"}` — 같은 기준을 다시 관찰하면 같은 문장으로 기록해 근거를 쌓는다. 지시서에서 관찰했으면 `brief`를 적는다.
- 쌓기 전에 정리: `ltm pref json`의 활성 기준과 뜻이 같으면 새로 만들지 말고 그 문장 그대로 기록한다.
- 묶기: 같은 묶음에 비슷한 기준이 3개 이상이면 아우르는 원칙으로 묶는다. `{"op":"group","statement":"<원칙 한 문장>","members":["p1","p4","p7"]}` (2단까지, 같은 묶음의 활성 최상위 기준만). 잘못 묶었으면 `{"op":"ungroup","id":"<원칙 id>"}`.
- 상한: 묶음 3~5개, 묶음당 최상위 항목 5개. 넘으면 합치거나 묶기를 사용자에게 한 줄로 제안한다. 확인 전이고 근거가 늘지 않은 채 지시서 5개가 지난 기준은 내려놓기를 제안한다(직접 내려놓지 않는다).
- 프로젝트 파일에서 알 수 있는 사실은 취향이 아니다. 기록하지 않는다.
- `statement`는 다음 작업에 적용할 수 있는 한 문장 기준. 일회성 지시·감정·개인정보는 기록하지 않는다.
- `evidence`는 관찰을 짧게 요약한다(원문 인용·민감 정보 금지).
- 사람의 GUI 행동도 근거다: `ltm check` 출력의 `brief.changes`(작성자 포함)에서 사람이 AI 추천과 다르게 고른 갈림길, 고치거나 지운 AI 항목을 보고 반복되는 기준을 기록한다.
- 기준이 없거나 충돌하고 되돌리기 어려운 선택이면 추측하지 말고 갈림길로 연다. 사람의 선택이 다음 근거가 된다.
- 현재 요청이 노트와 다르면 현재 요청을 따른다. 한 번의 예외로 노트를 바꾸지 않는다.
- 작업을 마칠 때 새로 기록하거나 근거가 늘어난 확인 전 기준을 한 줄로 알린다(GUI 취향 노트에서 확인).
- 사용자가 기준을 부정하면 `{"op":"retire","id":"p3"}`. id는 `ltm pref json`. 내려놓은 기준은 사용자만 다시 적용하며, 다른 문장으로 바꿔 다시 기록하지 않는다.

Issue `code` and change `event` contain codes and values. Explain them to the user in the conversation language. Markdown exports accept `--lang ko|en` (default: ko).

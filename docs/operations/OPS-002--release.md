# OPS-002 · 릴리스·게시

계약: INSTALL-001. 선택 이유: ADR-0009. 버전 원본은 `Cargo.toml`의 workspace 버전, 지원 플랫폼 원본은 `npm/listenee-ltm/platforms.json`이다.

## 버전 운영 계약

- 범위: LTM 제품 하나의 버전 `a.b.c`. Rust workspace·npm 런처·플랫폼 패키지·단독 실행 파일에 같은 버전을 적용한다. Git 태그는 `v<a.b.c>`다.
- 입력·시점: 출시 담당자가 마지막 공개 버전 이후의 변경과 사용자 영향을 검토해 출시를 결정할 때만 수동으로 올린다. 개발 커밋마다 버전이나 출시 PR을 만들지 않는다. 버전·변경 요약은 출시 변경 한 단위로 묶고, 기존 변경 단위에 포함할 수 있으면 별도 관리용 커밋·PR을 추가하지 않는다.
- 호환성 판단 대상: 문서화된 CLI 명령·옵션·JSON 출력, HTTP API, `.ltm` 저장 형식, 설치 요구사항·지원 플랫폼. 기존 사용자가 호출·설정·데이터를 바꾸어야 하면 호환성 변경으로 판단한다.

`1.0.0` 이후에는 [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html)을 따른다.

| 올릴 자리 | 기준 | 예 |
| - | - | - |
| `c` · PATCH | 호환성을 유지하는 오류·보안 수정 | `1.2.3 → 1.2.4`: 기존 명령의 잘못된 결과 수정 |
| `b` · MINOR | 호환되는 기능 추가 또는 공개 기능의 사용 중단 예고 | `1.2.3 → 1.3.0`: 선택 옵션 추가, 기존 옵션은 유지하며 폐기 예고 |
| `a` · MAJOR | 호환성을 깨는 공개 계약 변경 | `1.2.3 → 2.0.0`: 명령·필드 제거/이름 변경, 변환 없는 저장 형식 변경, 지원 플랫폼 제외 |

- 한 출시에는 가장 큰 변경 하나를 적용한다. MINOR를 올리면 PATCH를, MAJOR를 올리면 MINOR·PATCH를 0으로 만든다. 보안 수정도 심각도와 별개로 호환성을 기준으로 정한다.
- 현재 `0.x`는 SemVer상 불안정한 초기 개발 단계다. LTM 운영 규칙으로 호환되는 수정은 PATCH(`0.1.0 → 0.1.1`), 기능 추가·사용 중단 예고·호환성 변경은 MINOR(`0.1.1 → 0.2.0`)로 구분한다. 호환성 변경에는 영향과 이전 방법을 변경 요약에 명시한다. 공개 계약과 호환성 유지 책임을 확정할 때 `1.0.0`으로 전환한다.
- 문서·테스트·CI만 바뀌고 배포물·공개 계약에 영향이 없으면 버전을 유지한다. 현재 배포 구현은 숫자 버전만 지원하므로 `alpha`·`beta`·`rc` 태그는 사용하지 않는다.
- 완료 기준: 버전 값·태그·설치 안내가 일치하고, 변경 요약에 사용자 영향과 필요한 이전 방법이 있으며, 아래 산출물 검증을 통과한다. 변경 요약은 GitHub Release 본문에 모은다.
- 실패 복구: 검증 실패 시 게시 전에 후보를 수정한다. 공개한 버전·태그·파일은 덮어쓰거나 재사용하지 않고 새 버전으로 수정한다. 부분 게시 복구는 공개 릴리스 절차를 따른다.

## 산출물 검증

1. 프로젝트 라이선스는 MIT다. 원문 `LICENSE`와 Cargo·npm `license` 메타데이터가 일치하는지 확인한다. `pnpm gen:notices`로 의존성 고지를 갱신·검토한다. dry run과 태그 게시의 사전 검사는 동일하게 라이선스·고지 누락을 거부한다.
2. 변경을 검토하고 `pnpm check`를 통과시킨다. 설치 스크립트의 기본 버전·README 설치 URL도 배포 버전과 맞춘다.
3. 워크플로를 저장소에 반영한 뒤 `Release`를 브랜치에서 수동 실행한다. `workflow_dispatch`와 `codex/release-dry-run/**` 브랜치 push는 빌드·검증·패키징만 수행한다. 수동 실행은 기본 브랜치에 워크플로가 반영된 뒤 사용할 수 있으며, 그 전에는 검토한 동일 커밋을 전용 검증 브랜치에 push한다. 공개 게시는 태그 push에서만 수행한다. CI·CodeQL 및 저장소 보호 설정은 OPS-003을 따른다.
4. `release-assets` 아티팩트를 받는다. 세 OS의 실행 파일, 설치 스크립트, npm tarball 4개, `SHA256SUMS`가 있어야 한다. npm tarball마다 의존성 고지(공개 배포 시 프로젝트 LICENSE 포함)가 있어야 하며, 단독 실행 파일의 `ltm licenses`도 고지 원문을 출력해야 한다. 각 OS 작업은 빈 프로젝트 초기화·지시서 작성·내장 UI/API와 설치 테스트를 검증한다. Linux 정적 실행 파일은 런타임 없는 `scratch` 컨테이너에서도 검사하고, npm tarball은 Rust 없는 Node 컨테이너에서 오프라인 설치·실행을 검사한다.

아래 실행 방법 둘 중 하나를 선택한다.

```sh
# 기본 브랜치에 워크플로가 있으면 수동 실행
gh workflow run release.yml --ref dev
# 그 전에는 검토한 커밋으로 전용 dry run 실행(태그 생성 없음)
git push origin HEAD:refs/heads/codex/release-dry-run/0.1.0
gh run download <실행-id> --name release-assets --dir release-assets
cd release-assets
sha256sum --check SHA256SUMS
```

## npm 게시

태그 릴리스는 GitHub Release를 만든 뒤, npm 게시가 활성화된 저장소에서 플랫폼 3개 → 런처 순서로 OIDC·provenance 게시한다. 권한이 있는 유지보수 담당자가 게시 환경을 설정한다. 워크플로와 변수는 `.github/workflows/release.yml`이 원본이다.

공개 버전은 레지스트리에서 조회되고 tarball 무결성이 확인돼야 완료다. 서버 검사나 소유자 승인이 남아 있으면 같은 버전을 반복 업로드하지 않는다. 인증·Trusted Publisher 설정은 [npm 공식 안내](https://docs.npmjs.com/trusted-publishers/)를 따른다.

## 공개 릴리스와 다른 PC 확인

검토한 커밋에 workspace 버전과 같은 태그를 붙여 푸시하면 GitHub Release가 게시된다. npm 게시 작업은 위 변수를 켠 경우에만 실행된다. 최초 수동 게시한 버전을 다시 npm에 게시하지 않는다.

```sh
git tag v0.1.0
git push origin v0.1.0
```

다른 노트북의 빈 폴더에서 OPS-001의 한 줄 설치를 실행한다. 브라우저가 열리고, AI의 CLI 작성 → GUI 수정 → `ltm export`가 같은 데이터에 반영되어야 설치 완료로 판정한다. Windows·macOS의 보안 정책으로 실행이 차단되는지도 실제 PC에서 확인한다.

실패 시 아티팩트·실패 단계부터 확인한다. 이미 게시된 npm 버전은 덮어쓸 수 없다. 부분 게시라면 완료된 패키지는 재게시하지 말고 빠진 패키지부터 이어간다. 코드 변경이 필요하면 새 버전으로 다시 빌드한다. GitHub Release가 이미 있으면 해당 게시 작업 전체를 다시 실행하지 않는다.

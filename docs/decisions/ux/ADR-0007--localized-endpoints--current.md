# ADR-0007 · 문장은 끝단에서 만든다(다국어)

- 맥락: 코어가 한국어 문장(단계 이름, 막힘 메시지, 변경 요약)을 만들어 응답하고 파일에 저장했다. 언어를 추가하면 코어·저장 형식·UI가 함께 바뀌고, 저장된 기록은 언어를 바꿀 수 없다.
- 대안
  - A. 코어에 언어 인자를 넘겨 문장을 만든다: 저장된 변경 요약이 언어에 묶이고, 언어가 늘수록 코어가 표현을 떠안는다.
  - B. i18n 라이브러리(ICU 런타임·추출 도구) 도입: 문구 수(약 150개)에 비해 도구·빌드 비용이 크다.
  - C. 실행 중 LLM 번역: 결과가 매번 달라지고 오프라인·비용 문제가 있으며 검토할 원본이 남지 않는다.
  - D. 코어·저장·API는 코드와 값만 나르고(dumb pipe), 끝단이 언어별 정적 문구로 문장을 만든다(smart endpoints).
- 선택: D.
  - 코어·저장 파일·HTTP·CLI JSON: 문장 대신 코드(`IssueCode`, `ChangeEvent`)와 사용자가 쓴 값만 담는다. 단계 이름·안내도 담지 않는다.
  - 끝단 1, GUI: `ui/src/copy/<locale>/`의 언어별 문구. 기준 언어 `ko`의 형태가 타입이 되고, 다른 언어는 같은 형태를 만족해야 빌드된다. 복수형은 `Intl.PluralRules`로 처리한다.
  - 끝단 2, 최종 Markdown: 수신자용 결과물이라 코어 `render`가 만든다. 언어는 인자(`Locale`)로 받고, 고정 문구는 언어별 표에서 고른다. 항목 내용은 사용자가 쓴 언어 그대로 둔다.
  - 끝단 3, AI(CLI): 코드를 그대로 읽는다. 사람에게 설명하는 말은 AI가 대화 언어로 만든다.
  - 번역은 사람이나 LLM이 미리 써서 문구 파일에 둔다. 문구 파일이 원본이다.
- 이유: 저장 형식이 언어와 무관해져, 화면 언어를 바꾸면 과거 기록도 그 언어로 보인다. 표현이 바뀌어도 코어와 저장 형식은 그대로다.
- 결과
  - DATA-001: 변경 기록이 `event`(코드+값)가 된다. 예전 `summary` 문장은 `legacy`로 읽어 그대로 보여 준다.
  - 첫 지원 언어는 `ko`(기준)와 `en`이다. 화면 언어는 브라우저 언어로 정하고 사용자가 바꿀 수 있으며, 고른 언어를 기억한다. 없는 언어는 `ko`로 보여 준다.
  - Storybook `Copy/`에서 언어별 문구를 나란히 비교한다.
